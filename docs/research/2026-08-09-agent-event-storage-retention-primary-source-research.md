# Durable agent event storage and retention: primary-source research

Date: 2026-08-09 (Asia/Shanghai)
Scope: OpenAI Codex, OpenAI Agents SDK, LangGraph/LangChain, Temporal, and SQLite.
Purpose: define a crash-safe, bounded-growth design for Nexa's `agent_run_events`, checkpoints, compaction, retention, archival, and database maintenance after the `v113_normalize_agent_run_event_sequences` startup hang.

## Executive conclusion

The immediate hotfix and the long-term storage design are different changes:

1. **Hotfix now:** retire `v113` as a data rewrite. A run event sequence is a stable ordering cursor, not a promise that integers are dense. Existing gaps are valid and must not be repaired by rewriting millions of rows.
2. **Do not persist transport noise:** token/reasoning/output deltas, keepalives, and rapidly changing progress are stream events. Persist a coalesced chunk or final item, not one database row per callback.
3. **Separate fact history from current state:** keep a small append-only semantic ledger, plus a replaceable per-run snapshot/materialized projection through a known event cursor. Recovery reads the snapshot, then replays the suffix.
4. **Bound replay before deleting ancestors:** a retained snapshot must be sufficient to reconstruct the run. LangGraph explicitly warns that pruning deltas without a snapshot can silently reconstruct empty state.
5. **Make retention an explicit product policy:** active/interrupted/pinned runs are protected; closed runs can use configurable `keep_latest` or `delete` policies; large payloads can be moved to compressed archival storage. The user must be able to see usage, change the policy, delete data, and reclaim space.
6. **Run heavy work outside interactive startup:** compaction, pruning, archival, and file reclamation belong in bounded, resumable maintenance jobs. OpenAI's Agents SDK warns that compaction can delay turn completion and recommends running it between turns or while idle.
7. **Treat SQLite file maintenance separately from logical retention:** deleting rows frees pages for reuse but normally does not shrink the main database. `journal_size_limit` only trims a journal/WAL after a transaction or WAL reset; it cannot cap the temporary journal generated by one active multi-gigabyte transaction.
8. **Make data migrations resumable:** a large migration needs a monotonic cursor, bounded idempotent batches, durable progress, retryable skips, and a compatibility path. It must never hold the UI startup path inside one full-table transaction.

These conclusions are supported by the primary sources below. Exact Nexa thresholds and UX defaults are local product decisions; proposed starting values in this note are labeled as such.

## 1. What Nexa is doing today

At the examined Nexa baseline, `agent_run_events` uses `(run_id, event_seq)` as its primary key and has separate indexes for run, turn, and kind/time. The database API obtains the next position through `MAX(event_seq)`, writes with `INSERT OR REPLACE`, and reads one run with `ORDER BY event_seq` ([schema](../../crates/core/src/migrations/mod.rs), [read/write path](../../crates/core/src/db.rs)).

`v113_normalize_agent_run_event_sequences` creates a mapping for every event, calculates `ROW_NUMBER()` per run, then updates the full table twice: first to negative sequence values and then to the new positive dense values ([migration](../../crates/core/src/migrations/mod.rs)). On a database with millions of events, this is proportional to the entire table and index set, even when the only condition being "fixed" is a harmless gap.

The baseline connection already requests WAL mode and a 64 MiB `journal_size_limit` ([connection setup](../../crates/core/src/db.rs)). That setting does not make the `v113` transaction small. SQLite documents that `journal_size_limit` is checked after a transaction commits or after a WAL reset; it limits the journal left behind for reuse, not the live journal required to roll back an in-progress transaction ([journal size semantics](https://www.sqlite.org/pragma.html#pragma_journal_size_limit)). SQLite also says a very large write transaction can make the WAL very large because it cannot be reset in the middle of that transaction ([large WAL transactions](https://www.sqlite.org/wal.html#avoiding_excessively_large_wal_files)).

Therefore the startup hang is architectural, not a missing PRAGMA: the full-history rewrite should not exist on the startup path.

### 1.1 Production-shaped incident evidence

Read-only profiling was performed on an isolated copy of the affected local database after SQLite completed its hot-journal rollback. No message or tool content was printed. The recovered source had a 4,096-byte page size, 4,690,067 pages, no freelist pages, and a 19,210,514,432-byte main file. `v113` was not applied.

The principal growth drivers were structural:

| Store | Rows / payload | Evidence |
| --- | ---: | --- |
| `agent_run_events` | 2,549,827 rows | 1,863,403 `toolProgress` rows held about 7.32 GB of JSON; 858,285 events had no owning `agent_task_runs` row |
| `agent_task_run_events` | 871,339 rows | 695,709 legacy `tool` rows and 172,215 legacy `stream` rows duplicated the canonical run ledger and held about 3.63 GB of JSON |
| canonical chat data | 57 conversations, 13,943 messages, 379 turns | Counts were retained throughout the cleanup rehearsal |

The `toolProgress` shape showed the immediate write-amplification mechanism: provider argument streaming repeatedly serialized the complete cumulative `ToolRunUpdated` preview. This produced one growing snapshot per transport fragment instead of one bounded preview per display interval.

An offline rehearsal on the copy deleted orphan run events, removed replaceable progress from already terminal runs, removed the pre-v077 untyped task-event compatibility rows, dropped the primary-key-duplicate run index, and used `VACUUM INTO` to publish a new candidate. The candidate preserved all checked conversation, message, turn, task-run, terminal-event, tool-completion, output-delta, subtask, and verification counts; `PRAGMA quick_check` returned `ok`, the freelist was zero, and the resulting file was 1,959,604,224 bytes. This is incident evidence for an explicit offline reclamation path, not a proposal to run equivalent work during startup.

## 2. What leading runtimes actually persist

### 2.1 OpenAI Codex: filter first, append canonical items, compress cold files

Codex has an explicit persistence policy. It stores canonical response items and lifecycle markers but classifies raw response notifications, message/reasoning deltas, plan deltas, command output deltas, begin notifications, and many UI/transport events as transient ([policy entrypoint](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/policy.rs#L8-L35), [transient event list](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/policy.rs#L85-L182)). This is direct evidence for keeping Nexa's streaming protocol richer than its durable ledger.

Codex writes canonical session history as append-only JSONL. Its background writer keeps unwritten items in memory, drains only the successfully written prefix, retries after reopening the file, and exposes `persist`/`flush` barriers ([barrier contract](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/recorder.rs#L940-L979), [pending suffix and retry](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/recorder.rs#L1603-L1675), [drain-after-write](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/recorder.rs#L1730-L1770)). The source establishes process-level write recovery; it should not be over-read as a power-loss `fsync` guarantee for every record.

Cold rollout files are compressed in a fire-and-forget background worker so startup is not blocked. The current source considers a rollout cold after seven days, limits compression concurrency to two, rate-limits scans with a run marker, and coordinates compression with migration through a nonblocking maintenance lock ([background contract](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/compression.rs#L24-L30), [worker limits](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/compression.rs#L254-L261), [nonblocking launch and lock](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/compression.rs#L327-L415), [publish-after-revalidation](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/compression.rs#L627-L695), [maintenance exclusion](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/maintenance.rs#L1-L40)). Compression preserves the logical record stream while reducing cold physical storage; it is not a substitute for semantic retention.

Codex also avoids copying an entire parent ledger into a legacy child/subagent when it can prove a smaller replay is sufficient. It reverse-scans for a safe model-context checkpoint and returns the smallest bounded suffix; it falls back to full replay if safety cannot be proven ([bounded subagent replay](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/thread-store/src/local/rollout_migration/subagent.rs#L1-L58)).

Direct transfer to Nexa:

- filter durable events before storage;
- keep append identity stable;
- coalesce stream deltas into a final or bounded chunk item;
- compress/export cold detail in a background maintenance lane;
- resume from a verified checkpoint plus suffix instead of duplicating full history.

### 2.2 OpenAI Agents SDK: retrieval limits are not retention, compaction is scheduled work

The Agents SDK distinguishes how much history is *retrieved* from what remains stored. `SessionSettings(limit=N)` limits model input but does not alter session storage; the documentation explicitly says custom history filtering changes the model input while only new-turn items are persisted ([input filtering without re-persistence](https://openai.github.io/openai-agents-python/sessions/#control-how-history-and-new-input-merge), [retrieval limit](https://openai.github.io/openai-agents-python/sessions/#limiting-retrieved-history)). Nexa likewise should not confuse UI pagination or context-window trimming with disk retention.

`OpenAIResponsesCompactionSession` compacts stored history only after a trigger is met. The default implementation counts eligible candidate items and compacts after a threshold, then serializes mutation against snapshot/replace/restore with a lock ([candidate policy](https://github.com/openai/openai-agents-python/blob/e3d7c1727bf43761afbb7954651b7f908a973a3b/src/agents/memory/openai_responses_compaction_session.py#L24-L58), [compaction and mutation lock](https://github.com/openai/openai-agents-python/blob/e3d7c1727bf43761afbb7954651b7f908a973a3b/src/agents/memory/openai_responses_compaction_session.py#L135-L142), [compact then replace](https://github.com/openai/openai-agents-python/blob/e3d7c1727bf43761afbb7954651b7f908a973a3b/src/agents/memory/openai_responses_compaction_session.py#L168-L248)).

The official guide warns that automatic compaction can hold a streaming run open after the last token. It recommends disabling auto-compaction and invoking it between turns or during idle time when latency matters ([scheduling guidance](https://openai.github.io/openai-agents-python/sessions/#auto-compaction-can-block-streaming)). That is directly applicable to Nexa startup: even valid compaction is not an interactive-startup task.

The SDK's generic replacement helper clears, adds, and tries to restore on exceptions or cancellation ([replacement recovery](https://github.com/openai/openai-agents-python/blob/e3d7c1727bf43761afbb7954651b7f908a973a3b/src/agents/memory/openai_responses_compaction_session.py#L256-L369)). This is useful semantic evidence, but Nexa should not copy the clear/add sequence literally: because Nexa owns the SQLite implementation, its snapshot replacement and prune should happen in one database transaction or through a shadow table/file publish protocol so a process crash cannot land between clear and restore.

### 2.3 LangGraph: checkpoint lineage, pending writes, delta folding, and safe pruning

LangGraph saves graph state as checkpoints organized by thread, normally at each super-step. A `StateSnapshot` contains the current values, next nodes, metadata, tasks, and a parent checkpoint; pending writes from successful nodes are retained when another node fails, preventing successful work from being repeated on resume ([official persistence model](https://docs.langchain.com/oss/python/langgraph/persistence)).

The SQLite saver implements this as two separate tables: `checkpoints` keyed by thread/namespace/checkpoint and `writes` keyed by checkpoint/task/index, with parent checkpoint identity and WAL enabled ([SQLite schema](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/checkpoint-sqlite/langgraph/checkpoint/sqlite/__init__.py#L129-L164)). Checkpoint and pending-write inserts are idempotent by stable composite keys; thread deletion removes both tables together ([checkpoint put](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/checkpoint-sqlite/langgraph/checkpoint/sqlite/__init__.py#L387-L443), [pending writes and delete](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/checkpoint-sqlite/langgraph/checkpoint/sqlite/__init__.py#L445-L501)).

LangGraph's `DeltaChannel` is especially relevant to long agent output. It stores incremental writes and periodically materializes a full snapshot. Reducers must be deterministic and batching-invariant, and replay depth is bounded by both an update frequency and a global super-step limit ([delta contract and bounds](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/langgraph/langgraph/channels/delta.py#L25-L64), [restore/replay](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/langgraph/langgraph/channels/delta.py#L118-L157), [snapshot representation](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/langgraph/langgraph/channels/delta.py#L193-L200)).

Its pruning interface supports `keep_latest` and `delete`, but the primary source includes an important warning: naively keeping only the latest checkpoint can sever the delta chain and silently reconstruct empty state. Safe pruning must retain ancestors back to a complete snapshot or first materialize a new snapshot at the kept checkpoint ([pruning contract](https://github.com/langchain-ai/langgraph/blob/d56666f7fbf0d380ad84cdf0cbe5aa48ab0cc086/libs/checkpoint/langgraph/checkpoint/base/__init__.py#L374-L415)).

LangChain's hosted Agent Server makes retention explicit. Checkpoint TTL supports `delete` (remove the whole thread, runs, and checkpoints) and `keep_latest` (retain the thread and latest checkpoint while deleting older data), with a periodic bounded sweeper and per-thread overrides ([official TTL contract](https://docs.langchain.com/langsmith/configure-ttl#configuring-thread-and-checkpoint-ttl)). The documentation's 30-day value is an example, not a universal requirement.

Direct transfer to Nexa:

- store `run snapshot + semantic event suffix`, not an ever-growing full projection per event;
- make tool results/pending work independently idempotent;
- compact only after materializing a verified resume snapshot;
- make `keep_latest` and `delete` separate user-visible policies;
- never prune the chain needed to recover an interrupted run.

### 2.4 Temporal: append-only event identity, bounded histories, fresh runs, retention, archival

Temporal defines Event History as an append-only log that represents the full state of a Workflow Execution ([official glossary](https://docs.temporal.io/glossary#event-history)). It does not rewrite old event identities to make a history look nicer.

Temporal also treats unbounded history as a correctness and scalability problem. Its documented precautionary limit is 51,200 events or 50 MB, with warnings beginning at 10,240 events or 10 MB ([Workflow Execution limits](https://docs.temporal.io/workflow-execution/limits)). When a workflow history becomes long or large, `Continue-As-New` passes the latest relevant state into a new execution with the same Workflow ID, a new Run ID, and a fresh Event History ([Continue-As-New contract](https://docs.temporal.io/workflow-execution/continue-as-new)).

Closed histories have a namespace Retention Period; archival asynchronously copies closed Event Histories and visibility data to blob storage so they can outlive primary-store retention without overwhelming that primary store ([retention definition](https://docs.temporal.io/glossary#retention-period), [archival lifecycle](https://docs.temporal.io/temporal-service/archival)).

Nexa should borrow the separation, not Temporal's exact numerical limits:

- a run has an immutable local ledger identity;
- large or perpetual work starts a new run segment from a snapshot instead of rewriting the old segment;
- active and closed data have different policies;
- archival is a different storage tier from the operational database.

## 3. Recommended Nexa storage contract

This section is a local design inference from the sources above.

### 3.1 Three layers, three responsibilities

| Layer | Contents | Mutation rule | Default lifetime |
| --- | --- | --- | --- |
| `agent_runs` projection | status, phase, latest durable cursor, terminal summary, byte/event counters, last activity | small upsert in the same transaction as accepted semantic events | while the conversation/project exists |
| `agent_run_events` semantic ledger | lifecycle boundaries, accepted tool calls, approvals, final tool outcomes, errors, terminal events, bounded output chunks | append-only while hot; stable ID and cursor; gaps legal | detailed retention policy |
| `agent_run_snapshots` | reconstruction state through `through_event_seq`, including pending calls and accumulated visible output | replace latest only after complete deterministic materialization | retain for active/interrupted runs; keep latest for closed runs |

Large tool output, images, binary content, and exports should not be repeated inline in multiple JSON event rows. Store one content-addressed payload or artifact with hash, length, codec, and reference count; events point to it. This is a Nexa recommendation, not a claim that every examined runtime uses identical tables.

### 3.2 Event classification

| Event class | Stream to UI | Persist in semantic ledger | Notes |
| --- | --- | --- | --- |
| run/turn started, phase changed, approval requested/resolved, tool accepted, tool terminal outcome, error, done/cancelled | yes | always | required for recovery, audit, or terminal truth |
| output/reasoning token delta | yes | no row per token | fold in memory; persist bounded chunks and a final accumulated item/snapshot |
| keepalive, queue depth, elapsed time, transient progress percentage | yes | no | update counters/projection only if useful |
| large command/tool payload | preview | reference | bounded inline preview plus external/blob payload |
| debug telemetry | optional | separate bounded telemetry store | must not share retention with user history |

A practical coalescer can flush by any of: maximum encoded bytes, maximum elapsed time, semantic boundary, or terminal completion. Exact byte/time thresholds need profiling; they should not be hard-coded from another project.

### 3.3 Sequence and cursor rules

1. `event_seq` is immutable after commit.
2. Readers use `WHERE run_id = ? AND event_seq > ? ORDER BY event_seq LIMIT ?`; they never assume the next value equals `cursor + 1`.
3. A gap means "no durable record at this number," not corruption. If allocation currently happens before durability filtering, preserve the gap. New code may allocate only after filtering, but it must not rewrite old rows.
4. Add a stable `event_id` if events can be retried across process boundaries. Enforce idempotency with a unique key, not `INSERT OR REPLACE` over an already committed semantic event.
5. A run snapshot records `through_event_seq`. Recovery loads the newest valid snapshot and replays only events with a larger sequence.
6. If a required current-turn event fails to commit, fail/stop the turn explicitly. Do not hide the loss by closing a sequence gap.

Codex's paginated history similarly uses an exclusive ordinal and byte position to refer to an immutable prefix rather than deriving history identity from row count ([history position](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/protocol/src/protocol.rs#L3068-L3076), [ordinal resume](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/rollout/src/ordinal.rs#L56-L100)).

### 3.4 Snapshot and compaction rules

1. Snapshot creation is deterministic: replaying the same prefix produces the same snapshot.
2. Commit the snapshot and the projection cursor atomically. A snapshot is not usable until all required state is present.
3. Trigger snapshots by bounded work: semantic-event count, accumulated payload bytes, terminal boundary, or explicit idle maintenance.
4. Before pruning any event required for recovery, verify snapshot replay equivalence and record a compaction boundary/digest.
5. Never compact an active run on the UI thread or during app bootstrap. A foreground request may schedule work; the maintenance worker owns execution.
6. Keep tool-call/result pairs and approval/request/resolution pairs atomic under pruning.

### 3.5 Retention policy and user controls

Recommended policy shape:

- `keep_all`: no semantic pruning; cold payloads may still be losslessly compressed.
- `keep_latest`: for closed, unpinned runs, keep the latest reconstructive snapshot, terminal summary, important tool/error events, and any user-visible artifacts; prune older low-importance detail.
- `delete_after`: delete the entire closed run and unreferenced payloads after a configurable TTL.
- `project/conversation override`: active, interrupted, pinned, exported, or user-protected work does not expire.

Candidate starting defaults for product evaluation, not source-mandated values:

- coalesced raw stream chunks: eligible for pruning seven days after a successful terminal snapshot;
- closed unpinned detailed ledgers: `keep_latest` after 30 days;
- latest snapshot, terminal result, and user-created artifacts: retained with the conversation until explicit deletion;
- `delete_after` is opt-in or clearly disclosed, with a per-project override.

The Settings/Storage UI should show main DB bytes, WAL/journal bytes, reclaimable freelist bytes, event/payload bytes by project, current policy, next maintenance run, and last result. Controls should include "delete old detail," "delete conversation/project data," "export/archive," and "reclaim file space." Logical deletion and physical reclamation must be explained as separate operations.

## 4. SQLite growth and maintenance

### 4.1 WAL and journal policy

WAL improves local read/write concurrency, but it adds checkpointing as an explicit operation. SQLite auto-checkpoints at 1,000 pages by default; long-lived readers can prevent reset and allow the WAL to grow, while a very large write transaction can itself produce a very large WAL ([WAL checkpoint model](https://www.sqlite.org/wal.html#how_wal_works), [avoiding excessive WAL growth](https://www.sqlite.org/wal.html#avoiding_excessively_large_wal_files)).

Recommended Nexa behavior:

- retain WAL for the desktop workload;
- keep read transactions short and observable;
- run `wal_checkpoint(PASSIVE)` in a background maintenance lane and record returned WAL/checkpointed page counts;
- attempt `RESTART`/`TRUNCATE` only during an idle window after readers have drained, because those modes can block writers/readers while completing ([checkpoint modes](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint));
- keep `journal_size_limit`, but document that it acts only after commit/reset and is not an active-transaction quota ([journal size limit](https://www.sqlite.org/pragma.html#pragma_journal_size_limit));
- never delete a live or hot recovery journal/WAL file manually. SQLite states that a WAL is part of persistent database state and separating it can lose committed transactions or corrupt the database ([WAL file safety](https://www.sqlite.org/wal.html#the_wal_file)).

### 4.2 Reclaiming the main database

With the default `auto_vacuum=none`, deleting rows puts pages on a reusable freelist but does not shrink the database file. `VACUUM` rebuilds the file and reclaims space; `auto_vacuum=incremental` requires database-format support and explicit `incremental_vacuum(N)` calls ([auto-vacuum modes](https://www.sqlite.org/pragma.html#pragma_auto_vacuum), [incremental vacuum](https://www.sqlite.org/pragma.html#pragma_incremental_vacuum)).

For an existing large Nexa database:

1. First prune logically in small committed batches and let SQLite reuse freed pages.
2. Report `page_count`, `freelist_count`, page size, and estimated reclaimable bytes.
3. Offer explicit offline/idle reclamation only when there is enough disk. Ordinary `VACUUM` can require up to twice the original database size in free space ([VACUUM disk requirement](https://www.sqlite.org/lang_vacuum.html#how_vacuum_works)).
4. Prefer building and validating a new compact copy (for example `VACUUM INTO`) while leaving the original untouched, then close all connections and use Nexa's already-established atomic publication discipline. SQLite defines `VACUUM INTO` as a consistent snapshot but warns that an interrupted output can be incomplete; the original remains unchanged ([VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)).
5. For newly created databases, evaluate `auto_vacuum=incremental`; enabling it on an existing database itself requires a full `VACUUM`, so it is not part of the emergency hotfix.

### 4.3 SQLite runtime version

SQLite's official WAL page reports a rare WAL-reset race fixed in 3.51.3 and in patched 3.50.7/3.44.6 branches, affecting earlier versions under concurrent write/checkpoint timing ([official advisory](https://www.sqlite.org/wal.html#the_wal_reset_bug)). Nexa currently pins `rusqlite 0.32.1` / `libsqlite3-sys 0.30.1` with the bundled feature ([dependency](../../crates/core/Cargo.toml), [lockfile](../../Cargo.lock)). The implementation should query and log `sqlite_version()` at runtime, confirm whether the bundled source contains the fix, and upgrade to a fixed release before adding concurrent manual checkpoint workers. This note does not claim the shipped binary's effective SQLite version without that runtime verification.

## 5. Crash-safe migration design

Codex's current rollout migration is a strong primary-source pattern for replacing a startup-wide rewrite:

- it persists a monotonic creation-ordered cursor so later starts inspect only a bounded lookback/new suffix;
- it fingerprints malformed/skipped files by size and modification time, so unchanged failures do not block progress but changed data is retried;
- it advances the cursor only after a terminal migration snapshot;
- its cross-store publisher uses a durable `.pending` journal and removes it only after both the replacement history and SQLite state are complete ([migration state](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/state/src/runtime/rollout_migration.rs#L1-L76), [bounded startup inspection](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/thread-store/src/local/rollout_migration/startup.rs#L1-L114), [terminal frontier advancement](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/thread-store/src/local/rollout_migration/startup.rs#L116-L170), [durable cross-store journal](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/thread-store/src/local/rollout_migration/publish.rs#L1-L9), [journal fsync and parent sync](https://github.com/openai/codex/blob/646f7c0a91b8e327d263335da68ae8ef212895ce/codex-rs/thread-store/src/local/rollout_migration/publish.rs#L226-L267)).

For Nexa:

1. Startup migrations may create small schema/progress tables and indexes whose cost is known and bounded.
2. Any data backfill over unbounded user history becomes a separately versioned maintenance job.
3. Each job operates on a stable cursor (`run_id`, rowid, or created-at plus ID), processes a bounded byte/row budget, commits, records progress, and yields.
4. Batches are idempotent. Restart after any committed batch continues forward; restart during a batch rolls back only that batch.
5. The old read path remains compatible until the job finishes. Completion is recorded only after validation.
6. Progress, remaining bytes/rows, last error, and pause/cancel state are visible in Settings/Storage.
7. There is a single maintenance owner/lock so pruning, snapshot compaction, vacuum, migration, and checkpoint truncation cannot publish over one another.

SQLite transactions are atomic at the transaction boundary and `BEGIN IMMEDIATE` starts a write transaction immediately, but SQLite permits only one simultaneous writer ([transaction semantics](https://www.sqlite.org/lang_transaction.html)). Atomicity protects one bounded batch; it does not make an unbounded startup transaction responsive or storage-efficient.

## 6. Recommended delivery sequence

### P0 hotfix

- Remove the `v113` full-table renumbering from startup while preserving migration bookkeeping compatibility.
- Make recovery, replay, and UI ordering explicitly accept sparse monotonic sequences.
- Add regression fixtures with `1, 4, 7` and very large sequence values; assert cursor-based reads and append continue correctly.
- Do not delete the existing hot rollback journal. Let SQLite recover it.
- Prove startup does not issue a full-table `UPDATE agent_run_events` on an old multi-million-row fixture.

### P1 bounded-growth storage

- Add a durable-event classifier before `save_agent_run_event(s)`.
- Fold token/reasoning/output deltas; persist bounded chunks plus final accumulated output.
- Add `agent_run_snapshots` and per-run event/payload byte counters.
- Replace `INSERT OR REPLACE` for canonical events with idempotent insert semantics that cannot silently overwrite committed history.
- Add user-visible `keep_all`, `keep_latest`, and `delete_after` settings; protect active/interrupted/pinned runs.
- Add a bounded background sweeper and payload garbage collection.

### P2 physical maintenance and archival

- Add WAL/checkpoint/freelist observability and idle `PASSIVE` checkpointing.
- Verify/upgrade the bundled SQLite runtime before concurrent checkpoint work.
- Add cold compressed archival/export with checksums and atomic publication.
- Add explicit space reclamation using a validated compact copy, free-space preflight, progress, cancellation boundary, and safe rollback.
- Consider incremental auto-vacuum for new databases after workload benchmarks.

## 7. Required acceptance tests

1. **Sparse cursor:** persisted events `1, 4, 7` replay in order; `after=4` returns `7`; the next append does not rewrite prior rows.
2. **No delta explosion:** a simulated 100,000-token stream produces bounded durable chunks and one terminal snapshot, not 100,000 rows.
3. **Crash points:** interrupt before batch commit, after batch commit, after snapshot publish, and before progress advance; every restart converges without duplicates or missing terminal facts.
4. **Snapshot equivalence:** full replay and `snapshot + suffix` produce byte-equivalent reconstructive state for output, tool pairs, approvals, and terminal status.
5. **Prune safety:** `keep_latest` never prunes an active/interrupted/pinned run and never severs state needed by the retained snapshot.
6. **Retention idempotency:** repeated sweep runs delete the same logical set and garbage-collect payloads only when no references remain.
7. **Large database startup:** a representative multi-million-row database reaches an interactive window without data backfill or long write lock.
8. **WAL starvation:** a deliberately long reader makes `PASSIVE` checkpoint report incomplete progress without freezing the app; maintenance retries after the reader closes.
9. **Disk pressure:** reclamation refuses to start without safe free-space headroom and leaves the original database usable after cancellation or simulated power loss during output creation.
10. **Runtime gate:** logs/tests record the effective SQLite version and exercise concurrent writer/checkpoint behavior only on a release containing the WAL-reset fix.

## Final recommendation

The right emergency change is small: **stop renumbering and accept gaps**. The right long-term design is also clear: **persist semantic facts, project current state into a snapshot, fold stream noise, prune only behind a verified checkpoint, and move all heavy maintenance out of startup**.

No single PRAGMA can turn a 19 GB append-everything ledger into a bounded agent store. The storage bound comes from event classification and retention; SQLite checkpoint/vacuum policy then controls how that logical bound becomes physical disk reclamation.
